# DEPLOY.md: backend on Render (free plan)

How to put the backend API on Render, check it works, and what the free plan means for the demo. The frontend (Vercel) comes in T13.

What gets deployed: `render.yaml` (repo root) describes one free web service, built from `Dockerfile` in the Singapore region, next to the Neon database. Render rebuilds and redeploys on every push to `main` that touches the image (see "Build minutes").

> **The URL can be shared from T9 on; the sales key cannot.** `POST /api/chat` is rate limited per client IP (10 a minute, 100 a day), so the URL can go into the README (T14). `SALES_API_KEY` never goes into the README, the repo or the video (see PLAN.md, T14 note).

## The live service

| Item | Value |
|---|---|
| Service name | `vantis-sales-agent-api` (Blueprint from `render.yaml`) |
| Plan, region | Free, Singapore (same AWS region as the Neon project) |
| First deployed | 2026-10-11 (T6) |
| URL | In the Render Dashboard. It goes into the README in T14 |
| Measured warm | `/api/health` 0.13-0.23 s; `/api/chat` 1.0-1.8 s (Gemini 0.9-1.2 s of that) |

## One-time setup (about 10 minutes)

Before you start: `render.yaml`, `Dockerfile` and `.dockerignore` must be pushed to `main` on GitHub.

1. **Sign in.** Go to <https://dashboard.render.com> and choose **GitHub** to sign in (or sign up) with your GitHub account.
2. **New Blueprint.** In the Dashboard, click **New** (top right) → **Blueprint**.
3. **Give Render access to this one repo only.** Under "Connect a repository", click **Configure GitHub** (or "Configure account"). On GitHub's page for the Render app:
   - choose **Only select repositories**,
   - pick **vantis-sales-agent**,
   - click **Install** (or **Save**).
   Back on Render, the repo now shows in the list. Click **Connect** next to it.
4. **Name the Blueprint**, for example `vantis-sales-agent`. Render reads `render.yaml` and lists one web service, `vantis-sales-agent-api`, plan **Free**, region **Singapore**.
5. **Fill in the 3 secrets.** Render shows a field for each variable marked `sync: false`. Open `backend/.env` on your laptop and copy each value into the matching field:

   | Field in Render | Copy from `backend/.env` |
   |---|---|
   | `DATABASE_URL` | the `DATABASE_URL` line (the Neon direct connection string, `postgresql://…?sslmode=require`) |
   | `GOOGLE_API_KEY` | the `GOOGLE_API_KEY` line |
   | `GROQ_API_KEY` | the `GROQ_API_KEY` line |

   - Copy only the value after `=`. Leave out any quotes around it, and any spaces at either end.
   - Paste the keys only into Render's form. Never into a chat, an issue or a commit.
   - You don't type anything else. `SALES_API_KEY` is generated by Render, and the model names and other settings come from `render.yaml`.
6. Click **Deploy Blueprint**. Render builds the image (a few minutes the first time), starts it, and waits until `/api/health/live` answers. On Render the app starts within about 30 seconds (see "Free plan limits").
7. **Find the URL.** Open the service `vantis-sales-agent-api`. The URL is at the top of its page, like `https://vantis-sales-agent-api.onrender.com`. If that name was already taken on Render, the URL has extra characters (for example `vantis-sales-agent-api-x1y2.onrender.com`); always use the one Render shows.

## Check that it works

Wake the service and check the database and the KB: open `<URL>/api/health` in a browser. Expected:

```json
{"status":"ok","db":"ok","kb_chunks":54}
```

If the service was asleep, the first request takes about 30 seconds (32.5 s measured). Then check one chat answer (Git Bash):

```bash
curl -s -X POST <URL>/api/chat -H "Content-Type: application/json" \
  -d '{"message":"Do you provide installation in Delhi?"}'
```

Expected: an answer citing `[KB Section 10: Reference Service Locations]`, a source with `"section":"10"`, and `"degraded":false`. This proves that the prompts and the API keys made it into the deployed app. `/api/health` alone does not show that.

## Live check of T9 (sales API, key, chat limit): writes nothing to the main database

Every step below only reads, gets refused, or fails validation, so nothing is saved in the main database and no LLM is called. Do step 10 last: it locks your IP out of the sales API for 15 minutes. `<URL>` is the service URL; `<KEY>` is `SALES_API_KEY`.

1. **After the deploy**, open the service → **Environment** and check that `CLIENT_IP_HEADER` = `CF-Connecting-IP`, `CHAT_LIMIT_PER_MINUTE` = `10` and `CHAT_LIMIT_PER_DAY` = `100` are there. If the Blueprint sync did not add them, add them by hand and save. Copy the value of `SALES_API_KEY` (eye icon) to use below; don't paste it anywhere else.
2. Open `<URL>/api/health` and wait for `"status":"ok"` (about 30 s if it was asleep).
3. Open `<URL>/docs`. The endpoints are grouped (health, chat, sales); the sales ones show a lock icon. Open **GET /api/leads** → **Try it out** → **Execute** without authorizing → **401** `{"detail":"Missing or invalid API key. ..."}`.
4. Click **Authorize** (top right), paste the key, **Authorize**, **Close**. Then:
   - **GET /api/leads** → **200** `{"items": [...], "total": n, ...}`. Write down `total`.
   - **GET /api/leads** with `status` = `HOT` → **200**.
   - **GET /api/leads/{lead_id}** with `999999` → **404** `{"detail":"No lead with id 999999."}`.
   - **GET /api/support-requests** → **200**.
5. **POST /api/leads**, replace the example body with `{"name": "T9 check"}` → **422** with `missing_fields`. Then `{"phone": "123"}` → **422** with `errors.phone`. Neither saves anything.
6. **POST /api/callback** with `{"lead_id": 999999, "preferred_time": "tomorrow"}` → **404**; nothing saved.
7. **GET /api/leads** again: `total` is the same as in step 4, so nothing was written.
8. Chat limit, in Git Bash (empty messages are refused before the agent runs, but still count):
   ```bash
   curl -s -X POST <URL>/api/chat -H "Content-Type: application/json" \
     -d '{"message":"hi","session_id":"demo-1"}'
   # → 422, errors.session_id: "session_id must be the id from an earlier reply (a UUID v4); ..."
   for i in $(seq 1 11); do
     curl -s -o /dev/null -w "%{http_code}\n" -X POST <URL>/api/chat \
       -H "Content-Type: application/json" -d '{"message":""}'
   done
   # → 422 nine times (the demo-1 request counted too), then 429 twice
   curl -si -X POST <URL>/api/chat -H "Content-Type: application/json" -d '{"message":""}' | grep -iE "^HTTP|retry-after|detail"
   # → HTTP 429, a Retry-After header, and "You're sending messages a little fast. Please wait N seconds ..."
   ```
9. **The real client IP is used:** Render → service → **Logs**, search for `/api/chat`. Every request line from step 8 must show `"ip_source": "header"`. If any line says `"fallback"`, Cloudflare's header is not reaching the app and every visitor shares one limit: stop and check `CLIENT_IP_HEADER` on the Environment page.
10. **Spoofed headers don't help (do this last):**
    ```bash
    for i in $(seq 1 11); do
      curl -s -o /dev/null -w "%{http_code}\n" <URL>/api/leads -H "X-API-Key: wrong-$i" \
        -H "CF-Connecting-IP: 10.0.0.$i" -H "X-Forwarded-For: 10.1.0.$i"
    done
    # → 401 ten times, then 429: a fake IP header on each request did not give a fresh limit
    ```
    Requests without any key never count, so they can't cause this lockout. Your IP is locked out of the sales API for 15 minutes.
11. **Optional:** while locked out, open `<URL>/docs` on a phone using mobile data (not your Wi-Fi), authorize with the right key and run **GET /api/leads** → **200**. The limit is per real client, not one shared proxy bucket.

## Where things are in the Render Dashboard

| What | Where |
|---|---|
| The URL | Service page, top |
| Logs (JSON lines, one per request) | Service page → **Logs** |
| Deploy history, and whether a push started a build | Service page → **Events** |
| Environment variables, including the generated `SALES_API_KEY` (needed from T9 and T11) | Service page → **Environment** |
| Redeploy by hand | **Manual Deploy** (top right) → **Deploy latest commit**. Use **Clear build cache & deploy** if a build behaves oddly |

Changing a variable: edit it on the **Environment** page and save. Render redeploys with the new value. Variables added to `render.yaml` later are **not** asked for again (`sync: false` is only asked for when the Blueprint is first created), so add any new secret by hand on the Environment page.

## Free plan limits, and what they mean for the demo

| Limit | What it means |
|---|---|
| 0.1 CPU, 512 MB memory | The app uses about 100-115 MB, so memory is fine. The CPU is the slow part. Locally, with Docker limited to 0.1 CPU, starting the app took about 43 seconds (almost all of it Python loading FastAPI, LangChain and the Google client) and a chat answer about 6 seconds. On Render the CPU bursts higher for short work: a full wake takes about 30 seconds and warm chat answers take 1-2 seconds |
| Sleeps after 15 minutes without requests (Render says about 1 minute to wake) | Measured: the first request after 17 idle minutes took 32.5 seconds, including the app start. Render's own health checks do not keep it awake. **Open `<URL>/api/health` a minute before a demo or recording** and wait for `"status":"ok"`, and again if you pause for more than 15 minutes |
| 750 free instance hours a month per workspace | Enough for one service running all month |
| 500 build pipeline minutes a month (Hobby workspace) | Each image build takes a few minutes. `render.yaml` has a `buildFilter`, so pushes that change only docs or tests start no build. If the minutes run out, builds stop until next month (or until a payment method and a spend limit allow more) |
| Temporary filesystem, no shell, restarts possible | The app writes no files and keeps no state on disk (all data is in Neon), so a restart loses nothing |

## Health checks: why there are two

Render calls its health check path every few seconds while the service is awake. Each check must answer within 5 seconds, and after 60 seconds of failed checks Render restarts the service.

- **`/api/health/live`** (Render's check) answers `{"status":"ok"}` without touching the database, and is not logged. If Render used the full check, every call would query Neon. Neon could then never go to sleep while Render is awake, which spends free compute for nothing. And a slow Neon wake-up (the database connect timeout is 10 seconds) would count as a failed check, so Render would restart a healthy app, which can't fix a database problem anyway.
- **`/api/health`** (for us, and later the frontend's "server waking up" notice) checks the database and counts the KB chunks. It returns 200 with `"status":"degraded"` when the database is down.

## Local check with Docker (optional)

Start Docker Desktop, then from the repo root:

```bash
docker build -t vantis-api .
docker run --rm -p 10000:10000 --env-file backend/.env vantis-api
```

Add `--cpus=0.1 --memory=512m` to `docker run` to feel the free plan's speed. Note that `--env-file` keeps quotes as part of the value, so the values in `backend/.env` must not be quoted.
