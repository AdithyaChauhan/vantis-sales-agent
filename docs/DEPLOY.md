# DEPLOY.md: backend on Render (free plan)

How to put the backend API on Render, check it works, and what the free plan means for the demo. The frontend goes on Vercel in T13b: see "T13b steps" at the end.

What gets deployed: `render.yaml` (repo root) describes one free web service, built from `Dockerfile` in the Singapore region, next to the Neon database. Render rebuilds and redeploys on every push to `main` that touches the image (see "Build minutes").

> **The URL can be shared from T9 on; the sales key cannot.** `POST /api/chat` is rate limited per client IP (10 a minute, 100 a day), so the URL can go into the README (T14). `SALES_API_KEY` never goes into the README, the repo or the video (see PLAN.md, T14 note).

## The live service

| Item | Value |
|---|---|
| Service name | `vantis-sales-agent-api` (Blueprint from `render.yaml`) |
| Plan, region | Free, Singapore (same AWS region as the Neon project) |
| First deployed | 2026-10-11 (T6) |

## One-time setup (about 10 minutes)

Before you start: `render.yaml`, `Dockerfile` and `.dockerignore` must be pushed to `main` on GitHub.

1. **Sign in.** Go to <https://dashboard.render.com> and choose **GitHub** to sign in (or sign up) with your GitHub account.
2. **New Blueprint.** In the Dashboard, click **New** (top right) → **Blueprint**.
3. **Give Render access to this one repo only.** Under "Connect a repository", click **Configure GitHub** (or "Configure account"). On GitHub's page for the Render app:
   - choose **Only select repositories**,
   - pick **vantis-sales-agent**,
   - click **Install** (or **Save**).
   Back on Render, the repo now shows in the list. Click **Connect** next to it.
4. **Name the Blueprint**, for example `vantis-sales-agent`. Render reads `render.yaml` and lists one web service, `vantis-sales-agent-api`, plan **Free**, region **Singapore**.
5. **Fill in the 3 secrets.** Render shows a field for each variable marked `sync: false`. Open `backend/.env` on your laptop and copy each value into the matching field:

   | Field in Render | Copy from `backend/.env` |
   |---|---|
   | `DATABASE_URL` | the `DATABASE_URL` line (the Neon direct connection string, `postgresql://…?sslmode=require`) |
   | `GOOGLE_API_KEY` | the `GOOGLE_API_KEY` line |
   | `GROQ_API_KEY` | the `GROQ_API_KEY` line |

   - Copy only the value after `=`. Leave out any quotes around it, and any spaces at either end.
   - Paste the keys only into Render's form. Never into a chat, an issue or a commit.
   - You don't type anything else. `SALES_API_KEY` is generated by Render, and the model names and other settings come from `render.yaml`.
6. Click **Deploy Blueprint**. Render builds the image (a few minutes the first time), starts it, and waits until `/api/health/live` answers. On Render the app starts within about 30 seconds (see "Free plan limits").
7. **Find the URL.** Open the service `vantis-sales-agent-api`. The URL is at the top of its page, like `https://vantis-sales-agent-api.onrender.com`. If that name was already taken on Render, the URL has extra characters (for example `vantis-sales-agent-api-x1y2.onrender.com`); always use the one Render shows.

## Check that it works

Wake the service and check the database and the KB: open `<URL>/api/health` in a browser. Expected:

```json
{"status":"ok","db":"ok","kb_chunks":54}
```

If the service was asleep, the first request takes about 30 seconds (32.5 s measured). Then check one chat answer (Git Bash):

```bash
curl -s -X POST <URL>/api/chat -H "Content-Type: application/json" \
  -d '{"message":"Do you provide installation in Delhi?"}'
```

Expected: an answer citing `[KB Section 10: Reference Service Locations]`, a source with `"section":"10"`, and `"degraded":false`. This proves that the prompts and the API keys made it into the deployed app. `/api/health` alone does not show that.

## Live check of T9 (sales API, key, chat limit): writes nothing to the main database

**Passed on Render on 2026-10-11** (key required; 10 chat messages then 429 with Retry-After; `"ip_source": "header"` in the logs; lockout after 10 wrong keys).

Every step below only reads, gets refused, or fails validation, so nothing is saved in the main database and no LLM is called. Do step 10 last: it locks your IP out of the sales API for 15 minutes. `<URL>` is the service URL; `<KEY>` is `SALES_API_KEY`. For the curl steps, set the URL once in Git Bash:

```bash
BASE=https://vantis-sales-agent-api.onrender.com   # your URL from the Render Dashboard
```

> **`BASE` must not end with a slash.** `https://…onrender.com/` + `/api/chat` becomes `//api/chat`, which the app doesn't route, so every check fails for the wrong reason.

1. **After the deploy**, open the service → **Environment** and check that `CLIENT_IP_HEADER` = `CF-Connecting-IP`, `CHAT_LIMIT_PER_MINUTE` = `10` and `CHAT_LIMIT_PER_DAY` = `100` are there. If the Blueprint sync did not add them, add them by hand and save. Copy the value of `SALES_API_KEY` (eye icon) to use below; don't paste it anywhere else.
2. Open `<URL>/api/health` and wait for `"status":"ok"` (about 30 s if it was asleep).
3. Open `<URL>/docs`. The endpoints are grouped (health, chat, sales); the sales ones show a lock icon. Open **GET /api/leads** → **Try it out** → **Execute** without authorizing → **401** `{"detail":"Missing or invalid API key. ..."}`.
4. Click **Authorize** (top right), paste the key, **Authorize**, **Close**. Then:
   - **GET /api/leads** → **200** `{"items": [...], "total": n, ...}`. Write down `total`.
   - **GET /api/leads** with `status` = `HOT` → **200**.
   - **GET /api/leads/{lead_id}** with `999999` → **404** `{"detail":"No lead with id 999999."}`.
   - **GET /api/support-requests** → **200**.
5. **POST /api/leads**, replace the example body with `{"name": "T9 check"}` → **422** with `missing_fields`. Then `{"phone": "123"}` → **422** with `errors.phone`. Neither saves anything.
6. **POST /api/callback** with `{"lead_id": 999999, "preferred_time": "tomorrow"}` → **404**; nothing saved.
7. **GET /api/leads** again: `total` is the same as in step 4, so nothing was written.
8. Chat limit, in Git Bash (empty messages are refused before the agent runs, but still count):
   ```bash
   curl -s -X POST "$BASE/api/chat" -H "Content-Type: application/json" \
     -d '{"message":"hi","session_id":"demo-1"}'
   # → 422, errors.session_id: "session_id must be the id from an earlier reply (a UUID v4); ..."
   for i in $(seq 1 11); do
     curl -s -o /dev/null -w "%{http_code}\n" -X POST "$BASE/api/chat" \
       -H "Content-Type: application/json" -d '{"message":""}'
   done
   # → 422 nine times (the demo-1 request counted too), then 429 twice
   curl -si -X POST "$BASE/api/chat" -H "Content-Type: application/json" -d '{"message":""}' | grep -iE "^HTTP|retry-after|detail"
   # → HTTP 429, a Retry-After header, and "You're sending messages a little fast. Please wait N seconds ..."
   ```
9. **The real client IP is used:** Render → service → **Logs**, search for `/api/chat`. Every request line from step 8 must show `"ip_source": "header"`. If any line says `"fallback"`, Cloudflare's header is not reaching the app and every visitor shares one limit: stop and check `CLIENT_IP_HEADER` on the Environment page.
10. **A spoofed header doesn't help (do this last):** send wrong keys with only a fake `X-Forwarded-For`, a different one each time:
    ```bash
    for i in $(seq 1 11); do
      curl -s -o /dev/null -w "%{http_code}\n" "$BASE/api/leads" -H "X-API-Key: wrong-$i" \
        -H "X-Forwarded-For: 10.1.0.$i"
    done
    # → 401 ten times, then 429: a fake X-Forwarded-For on each request did not give a fresh limit
    ```
    Don't fake `CF-Connecting-IP` here. On Render, Cloudflare refuses such a request with **403** (`text/plain`, not the app's JSON) before it reaches the app, so that header can't be spoofed at all, and the loop would test Cloudflare instead of the app.
    Requests without any key never count, so they can't cause this lockout. Your IP is locked out of the sales API for 15 minutes.
11. **Optional:** while locked out, open `<URL>/docs` on a phone using mobile data (not your Wi-Fi), authorize with the right key and run **GET /api/leads** → **200**. The limit is per real client, not one shared proxy bucket.

## Where things are in the Render Dashboard

| What | Where |
|---|---|
| The URL | Service page, top |
| Logs (JSON lines, one per request) | Service page → **Logs** |
| Deploy history, and whether a push started a build | Service page → **Events** |
| Environment variables, including the generated `SALES_API_KEY` (needed from T9 and T11) | Service page → **Environment** |
| Redeploy by hand | **Manual Deploy** (top right) → **Deploy latest commit**. Use **Clear build cache & deploy** if a build behaves oddly |

Changing a variable: edit it on the **Environment** page and save. Render redeploys with the new value. Variables added to `render.yaml` later are **not** asked for again (`sync: false` is only asked for when the Blueprint is first created), so add any new secret by hand on the Environment page.

## Free plan limits, and what they mean for the demo

| Limit | What it means |
|---|---|
| 0.1 CPU, 512 MB memory | The app uses about 100-115 MB, so memory is fine. The CPU is the slow part. Locally, with Docker limited to 0.1 CPU, starting the app took about 43 seconds (almost all of it Python loading FastAPI, LangChain and the Google client) and a chat answer about 6 seconds. On Render the CPU bursts higher for short work: a full wake takes about 30 seconds and warm chat answers take 1-2 seconds |
| Sleeps after 15 minutes without requests (Render says about 1 minute to wake) | Measured: the first request after 17 idle minutes took 32.5 seconds, including the app start. Render's own health checks do not keep it awake. **Open `<URL>/api/health` a minute before a demo or recording** and wait for `"status":"ok"`, and again if you pause for more than 15 minutes |
| 750 free instance hours a month per workspace | Enough for one service running all month |
| 500 build pipeline minutes a month (Hobby workspace) | Each image build takes a few minutes. `render.yaml` has a `buildFilter`, so pushes that change only docs or tests start no build. If the minutes run out, builds stop until next month (or until a payment method and a spend limit allow more) |
| Temporary filesystem, no shell, restarts possible | The app writes no files and keeps no state on disk (all data is in Neon), so a restart loses nothing |

## Keep-warm during the review (T14)

`.github/workflows/keep-warm.yml` calls `GET /api/health/live` every 10 minutes from 08:00 to 23:00 IST, so reviewers don't wait for a cold start.
- **Schedule:** GitHub reads cron in UTC, so the file has three cron lines for 02:30-17:30 UTC. `tests/test_deploy_config.py` checks they give exactly 08:00, 08:10, …, 23:00 IST.
- **Why `/api/health/live`:** it doesn't query the database, so Neon still sleeps between chats. `/api/health` would wake Neon on every ping and use up its free compute hours.
- **Free hours:** it keeps the Render service awake for about 15 hours a day, well within the 750 free instance hours a month.
- **Late runs:** GitHub can start a scheduled run a few minutes late, so a cold start can still happen now and then. The page's waking note covers it.
- **Not a deploy:** the workflow file is outside `buildFilter`, so it starts no Render build.
- **Manual run:** Actions → "Keep the API warm" → **Run workflow** (`workflow_dispatch`).
- **Switch it off after the review:** GitHub → Actions → "Keep the API warm" → "..." → **Disable workflow**. Or run `gh workflow disable keep-warm.yml`, or delete the file.

## Health checks: why there are two

Render calls its health check path every few seconds while the service is awake. Each check must answer within 5 seconds, and after 60 seconds of failed checks Render restarts the service.

- **`/api/health/live`** (Render's check) answers `{"status":"ok"}` without touching the database, and is not logged. If Render used the full check, every call would query Neon. Neon could then never go to sleep while Render is awake, which spends free compute for nothing. And a slow Neon wake-up (the database connect timeout is 10 seconds) would count as a failed check, so Render would restart a healthy app, which can't fix a database problem anyway.
- **`/api/health`** (for us, and later the frontend's "server waking up" notice) checks the database and counts the KB chunks. It returns 200 with `"status":"degraded"` when the database is down.

## Local check of the chat page (and later the dashboard) without touching main

For trying the page on your laptop. Leads, callbacks and support requests go to the Neon **test** branch, never main.

1. Terminal 1 (Git Bash):
   ```bash
   cd backend && source .venv/Scripts/activate && python -m scripts.serve_test_branch
   ```
   It prints "Leads, callbacks and support requests are on the test branch." and serves the API on `http://127.0.0.1:8000`.
   - The chat agent's lead writes and the sales API both use `TEST_DATABASE_URL`. The KB and service areas are only read from main, and chat memory stays in the process (a restart forgets the chats).
   - It refuses to start if `TEST_DATABASE_URL` is empty or the same as `DATABASE_URL`.
   - It sets `CORS_ORIGINS=http://localhost:5173` and `CHAT_SHOW_LEAD_SCORE=true` unless they are already in the environment.
   - For the dashboard (T11), give it a throwaway key: `SALES_API_KEY=any-local-key-of-16-chars python -m scripts.serve_test_branch`.
2. Terminal 2:
   ```bash
   cd frontend && npm install && npm run dev
   ```
   Then open <http://localhost:5173>. The page calls `http://127.0.0.1:8000` unless `VITE_API_URL` says otherwise (`cp .env.example .env.local`).
   The sales dashboard (T11) is at <http://localhost:5173/leads>: enter the throwaway key from step 1. For demo data run `python -m scripts.seed_demo_leads` (test branch) once; the backend tests empty those tables, so run it again after them.
3. Phone width: Edge or Chrome DevTools (F12) → device toolbar (Ctrl+Shift+M) → **Responsive**, width 400. Dark mode: DevTools → **⋮** → More tools → **Rendering** → "Emulate CSS media feature prefers-color-scheme: dark".

Use `127.0.0.1`, not `localhost`, for the API. uvicorn listens on IPv4 only, and `localhost` can resolve to IPv6 `::1` first; on this laptop a Docker/WSL relay listens on port 8000 there and answers 404. The plain `uvicorn app.main:app --port 8000` writes chat leads to **main**: use it only when that is what you want.

## T13b steps: the frontend on Vercel

Do these in order. **No secret goes into Vercel.** Vite copies every `VITE_` variable into the public JavaScript, and the sales key is never one of them: staff type it into the dashboard page, which keeps it in that browser tab only.

### 1. The Vercel project

1. On <https://vercel.com>, click **Add New… → Project**. Import the GitHub repo `vantis-sales-agent`; when GitHub asks, give Vercel access to this repo only.
2. On the import screen, set:

   | Setting | Value |
   |---|---|
   | Root Directory | `frontend` (click **Edit** and pick the folder) |
   | Framework Preset | **Vite** (detected from `frontend/package.json`) |
   | Build Command | `npm run build` (the default) |
   | Output Directory | `dist` (the default for Vite) |
   | Install Command | the default (`npm install`; `package-lock.json` pins every version) |
   | Environment Variable | `VITE_API_URL` = the Render URL from the service's page, for example `https://vantis-sales-agent-api.onrender.com` (no path; a trailing slash is fine). Environment: **Production** |

3. Click **Deploy**. Write down the production URL (the project's **Domains**), for example `https://vantis-sales-agent.vercel.app`.

Notes:
- `VITE_API_URL` is read when Vercel **builds** the page. Vercel's docs: changes to environment variables "only apply to new deployments", so after changing it, redeploy.
- `frontend/vercel.json` (T13a) sends every page path to `/index.html`, so `/leads`, `/leads/<id>` and `/support` survive a refresh or a shared link. Vercel serves real files such as `/assets/…` first.

### 2. Render: allow the Vercel site (CORS)

`CORS_ORIGINS` must be **the Vercel production URL only**, written exactly as the browser sends it in the `Origin` header:

```
https://vantis-sales-agent.vercel.app
```

- **Format:** scheme and host only, with no trailing slash, no path and no `*`. The backend splits the value on commas and compares each origin exactly (`app/core/config.py`, `cors_origin_list`).
- **Not included:** Vercel's preview URLs (one per branch or commit, ending in `.vercel.app`) stay blocked on purpose. `http://localhost:5173` is not included either: local checks run `serve_test_branch` on the laptop, which reads `backend/.env`.
- **Change it in `render.yaml`, not only in the Dashboard.** It is a plain `value` in the Blueprint, and Render's Blueprint docs say a sync "can create new environment variables or modify the values of existing ones", so a Dashboard-only edit could be overwritten on the next sync.

The steps (1 and 2 done in T13b; `test_cors_allows_only_the_vercel_production_site` pins the value):
1. `render.yaml`: set the `CORS_ORIGINS` value to the URL above.
2. `backend/tests/test_deploy_config.py`: add `"CORS_ORIGINS"` to `PROD_DIFFERS` with the reason ("the Vercel production URL; local runs use http://localhost:5173"). That test compares `render.yaml` with `backend/.env.example`.
3. Run the backend tests, commit (`/handoff`) and push.
4. Auto Sync is on by default: Render applies the Blueprint change on the push and redeploys (Render's docs: "Each push to the linked branch that modifies your Blueprint file triggers a deploy of any added or modified resources"). To confirm after the push:
   - **Blueprints** → `vantis-sales-agent` → **Settings**: **Auto Sync** says **Yes**, so there is nothing to click. Only if it says **No** (or the value below hasn't changed a few minutes after the push), click **Manual Sync** on the Blueprint's page.
   - The service → **Environment**: `CORS_ORIGINS` is exactly `https://vantis-sales-agent.vercel.app`.
   - The service → **Events**: the newest deploy, started after the push, is live. A push that also changes `backend/app` or `prompts` builds a new image anyway (`buildFilter`).
   - The two curl checks below.

Check what Render answers the browser (Git Bash). These are the browser's CORS preflights: the CORS middleware answers them before any route, so they use no AI call and don't count toward the chat limit.

```bash
BASE=https://vantis-sales-agent-api.onrender.com   # your URL from the Render Dashboard, no trailing slash
curl -s "$BASE/api/health"   # wakes the service first (about 30 s if it was asleep): "status":"ok"

# 1. The Vercel site is allowed
curl -si -X OPTIONS "$BASE/api/chat" -H "Origin: https://vantis-sales-agent.vercel.app" \
  -H "Access-Control-Request-Method: POST" -H "Access-Control-Request-Headers: content-type" \
  | grep -iE "^HTTP|^access-control-allow-origin"
# → status 200, and: access-control-allow-origin: https://vantis-sales-agent.vercel.app

# 2. Any other site is still refused
curl -si -X OPTIONS "$BASE/api/chat" -H "Origin: https://example.com" \
  -H "Access-Control-Request-Method: POST" -H "Access-Control-Request-Headers: content-type" \
  | grep -iE "^HTTP|^access-control-allow-origin|disallowed"
# → status 400 and "Disallowed CORS origin", with no access-control-allow-origin line
```

If the first check still answers 400 while the Environment page shows the new value, the running instance started before the change: **Manual Deploy** → **Deploy latest commit**.

### 3. Checks after both deploys

- Open `<vercel-url>/leads/1` directly, and refresh `<vercel-url>/support`. Both pages load (no Vercel 404).
- Send one chat message. DevTools (F12) → **Console** shows no CORS error, and **Network** shows `/api/chat` with status 200.
- After Render's service has slept (15 idle minutes), open the page.
  - The note "Waking up the server. The first reply can take up to a minute." shows at the top within about 2 seconds, and goes away when the server answers (30-40 s).
  - A warm visit shows no note. A slow chat reply only says "Still working on it. This can take up to a minute." after 8 seconds.
- The dashboard asks for the sales key; nothing in Vercel's settings holds it.
