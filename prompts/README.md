# Prompts

Every LLM prompt lives here as a `.md` file. Code loads them with `load_prompt(name)` (`backend/app/core/prompts.py`); no prompt text is written in code. Each file holds only the prompt text.

| File | Used by | Purpose |
|---|---|---|
| `system_prompt.md` | The agent node (`app/agent/graph.py`), as the system message | Role, tone, KB-only rule, citation rule, at most one follow-up question, the never-invent list (KB Section 16), off-topic redirect, KB and user text treated as data. T8a: tool policy (`search_knowledge_base`, `check_service_area`), how to word listed and unverified cities, list every offering, short replies, no claimed actions. T8b: the four lead tools, contact requests first, one question for up to two details, city confirmation, gentle next step, never a score or status. T10b: plain words (no copied KB text or office terms), numbered lists, each KB section cited once with its full label and never a tool, an offer after information questions and details only after interest, unlisted cities explained once in its own words. T12a: citations only on facts from this turn (never on a question, a thank-you, a confirmation or a request for details), state the KB's specific terms, an offer that follows from the answer, never ask for a known detail, one detail per reply after saving, the rooftop as "usable roof space", the "updated" callback wording. T12b: offers only what the KB or a tool can deliver, the package that matches a stated size, "service areas" (never "reference locations"), a part the context doesn't answer said plainly (no invented staff, policies or services), cities checked by the system before the model. T13b: a monthly bill alone never picks a package (name the reference packages for their kind of property in the KB's words, and a site assessment decides which one fits; never one package for the bill, never a bill range; ask home or business first when that isn't known), and the offer "which reference package fits their monthly bill" became "the reference packages for their home or business". Code guards back these up (`app/rag/answer.py`, `app/agent/leads.py`) |
| `lead_qualification_prompt.md` | `app/leads/reason.py`, sent to `reason_llm` (T13d: the fast model, 8 s, after the reply, so it never uses the main model's quota; T12a had moved it to the main model, 4 s) | Writes the one-sentence `reason` for a lead's status from the score breakdown only (status, score, rule labels with points, caps, city, and T12a: what keeps the lead from the next status, which the sentence must end with). It never sees a name, phone, email or money amount. It must not mention prices, savings, subsidies, financing, EMIs, guarantees or dates (KB Section 16). Code checks the reply and uses a template sentence when it is empty, too long, more than one sentence, names another status or touches a forbidden topic; T12b: the model writes only the first part, code adds the "not … yet" ending once, and a reply that copies the prompt's wording or repeats the ending gets the template. Placeholders: `{status}`, `{score}`, `{city}`, `{factors}`, `{caps}`, `{ending}` |
| `rag_prompt.md` | The agent node, wrapping the customer's latest message | Shows the retrieved chunks inside `<context>`, each starting with its label `[KB Section N: Title]`; sets the citation format; says what to do when the context does not cover the question. T8b: the `<lead_progress>` block (built in code: field names and what is still needed, never personal values, never a score; T10b: says not to ask for details while the customer has only asked for information). T10b: each KB section cited once, never a tool. T12a: cite only this message's context or this turn's tool results, and only after a fact. T12b: the `<service_area_check>` block (the system's check of every city named) and a "Before you reply, check" list after the message, read last by every model. T13b: `{package_guidance}` right after the context, filled on a package turn and removed with its line otherwise. Placeholders: `{context}`, `{package_guidance}`, `{lead_progress}`, `{service_area_check}`, `{question}` (filled with `str.replace`, the customer's text last) |
| `package_guidance_prompt.md` | The agent node (`package_guidance` in `app/agent/graph.py`), inside `rag_prompt.md` right after the context, only on a package turn (`package_case` in `app/agent/leads.py`: the monthly bill, or the property type after it, while no system size is settled; not in a support case or on a contact request) | T13b: the bill-turn package rule next to the KB Section 9 rows. KB Sections 8 and 9 give no bill ranges, so a bill alone never picks a package: for a home or a business, name every reference package KB Section 9 gives for it with its short description, cite it once, and say a site assessment decides which one fits; while the type is unknown, ask whether it is a home or a business, and name no package. Placeholder: `{property}` ("home", "business" or "unknown", from the lead's `customer_type`) |
| `lead_extraction_prompt.md` | The understand node (`app/agent/understand.py`), sent with structured output to `understand_llm` (T13d: the main model, then fast, each cut off after 4 s; Groq is kept for answers, and a failed understand step reads details in code; T12a: main, Groq, fast; T10b: main, fast, Groq, 5 s) | Intents (question, buying interest, greeting, reply to the assistant, thanks or bye, existing-customer issue, off-topic; T8b: contact request, gives details; T12a: asks what is needed, T12b: only for the customer's own details), a standalone `search_query` in the KB's own words, the lead details the customer stated (`LeadData` field names and descriptions), and (T12b) `cities`, every city the message names; T13b: the kind of place fills `customer_type` (a home of any kind: residential; a shop, office or other business: commercial). Gets the KB section titles and the KB Section 8 summary chunk from the database, and the last 6 messages. Placeholders: `{section_titles}`, `{catalog}`, `{history}`, `{message}` (filled last) |
